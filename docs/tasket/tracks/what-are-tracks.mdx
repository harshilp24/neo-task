**Tracks** let one task move through several workstreams at the same time, with a separate status in each. A project's tracks might be Spec, Design, Engineering and QA. Each discipline sees the task in its own column and moves it forward without changing anyone else's progress, while the task itself stays in one place.

- **One task, many lanes.** A task can be *Pending* on Design while it's *Done* on Spec. Its comments, assignees, watchers, Studio docs and Friday chat stay on the one task.
- **Separate from the task's own status.** Marking a task Done on a track doesn't complete the task, and completing the task doesn't change its tracks.
- **Scoped to a project.** Each project has its own tracks. A track in one project doesn't exist in any other.

This page explains why Tracks exist, how they work, and when to use them. It has no steps. To set Tracks up, follow [Get started with Tracks](./get-started.mdx).

## Why one status isn't enough

A task's status answers one question: is the work open or closed? Real work usually passes through several teams before it closes, and those teams overlap.

Take a sign-in redesign. It needs a spec, then design, then engineering, then QA, then documentation, and the task can be in spec and in design at the same time. Ask *"Where is the sign-in redesign?"* and the honest answer is "spec is done, design is under way, engineering hasn't started". A single Open status can't hold that.

Splitting the work into one task per discipline doesn't fix it either. The comments, docs and Friday chat split across copies, so nobody sees the whole picture.

Tracks keep one task as the single home for the work and its context, and give each workstream its own status on it.

## How Tracks work

A track is a workstream in a project, such as Design. A task joins a track when someone **starts** it there. From then on it has a status on that track, either *Pending* while the work is under way or *Done* when that workstream has finished with it. On every track it hasn't joined, the task is *Not started*.

Two views show the same information from different sides:

- **The Tracks board** puts the tracks side by side, one column per track. Read it to see what one team has on its plate: a task on three tracks appears in three columns.
- **The Tracks pill** on a task lists every track in the project with the task's status on each. Read it to see where one task stands across every team. It's the only place that shows the whole picture for a single task.

The task's own status, *Open*, *Completed* or *Discarded*, runs alongside its tracks and doesn't depend on them. A task can be *Done* on every track and still *Open*, waiting for someone to complete it. Completing it takes it off the board, but its track statuses are kept and come back if it's reopened.

## How Tracks differ from a status board

The Tracks board looks like the boards in other tools, but its columns mean something different:

| | Status board | Tracks board |
|---|---|---|
| A column is… | a stage in one workflow, such as *In review* | a workstream that runs in parallel, such as *Design* |
| A task is in… | exactly one column | as many columns as it has tracks |
| Moving a task… | changes its status | changes its status on that track only |
| "Done" means… | the task is finished | that workstream has finished with it |

If your team moves a task through stages one after another and only one team works on it at a time, project sections or the task's own status are enough. Tracks are for work that several teams carry at once.

## When to use Tracks

Use Tracks when the tasks in a project pass through the same set of workstreams, and those workstreams overlap or hand work to each other, as a product feature does on its way through spec, design, engineering, QA and documentation.

Skip Tracks when a task belongs to one discipline, or one person takes it from start to finish. Several assignees on one task don't need Tracks.

## What to know before you turn them on

A few things about Tracks are hard to change later:

- **Name tracks after workstreams, not stages.** "Design" works as a track; "In review" works better as a section.
- **Deleting a track or turning Tracks off can't be undone.** Both remove track statuses from every task, closed ones included. Renaming and reordering tracks are always safe.
- **Moving a task to another project clears its tracks**, because tracks belong to a project. The task arrives *Not started* everywhere, even on a track with the same name.

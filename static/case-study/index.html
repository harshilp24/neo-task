Task 1

What I'd need clarified

The briefList everything you would need clarified before you could write accurate documentation from the extract. For each item, state the assumption you took in order to complete the document.

I read the PRD as a spec I'd be held to and checked it against the real Tracks screen on neo.work. That gave 24 questions: 6 about data loss and permissions, 12 about behaviour, and 6 about labels and wording. Each has the assumption I took and the pages it affects. Where the PRD could cost someone data, I took the reading that protects it.

The three that matter most

  1. Turning Tracks off: hide or delete?

    One section says switching off "is a hide, not a delete" and everything comes back. The lifecycle rules say it "clears all track assignments".

    Assumed: it clears everything, and the docs warn before the step.

  2. Who can delete a track?

    Deleting is permanent and reaches closed tasks, but the permissions table has no row for it. A user story says any team member.

    Assumed: any member, as the story says, with a recommendation to make it admin-only.

  3. What does Stop do?

    Stop is listed as an action but never defined, and it's missing from the offline list.

    Assumed: it returns the task to Not started, and needs a connection.

Task 2

The Tracks docs

The briefWrite three pieces on the same feature: a user-facing feature document for someone using the feature for the first time, a how-to guide for someone with a specific task in hand, and a release note for an existing user scanning what changed.

I built the docs as a small Docusaurus site, kept in Git, instead of a Google Doc. Each page answers one kind of need (Diátaxis), so every step and rule lives in one place and the other pages link to it.

Task 3

The write-docs skill

The briefBuild a reusable skill file that produces a first draft of those same three article types from any PRD and its supporting artefacts, not just this one.

The skill is a folder of plain Markdown, write-docs/, that any AI assistant or writer can follow. Give it a PRD and any screens, and it drafts the full set of pages from Task 2, a release note, the clarifying questions, and a report of what it checked. When the feature changes later, it updates the one page that owns each changed fact.

Write-docs skill

An agent skill for drafting Neo product documentation from a PRD. Give it a PRD and any screens or tickets, and it produces first drafts of every page a feature needs, plus a list of questions the PRD leaves open.

Architecture overview

The skill handles task-specific jobs through workflows, and reuses shared modules and framework rules for everything else.

Execution flow
SKILL.md (routing)
 └─> workflows/  (one per kind of job)
      ├─> modules/  (PRD analysis, page planning, doc contracts, content generation)
      │    └─> framework/  (Diátaxis, style and tone, linking, callouts, files, personas)
      └─> quality/checklist.md  (shared checks)

How to run it

  1. Give it the inputs. The PRD, plus any screenshots or tickets. Screens win over the PRD for labels.
  2. Ask in plain words.Use write-docs to draft the docs for this PRD.
  3. Review what comes back. The pages, the release note, the clarifying questions with assumptions, and a checklist report.

To change how every page is written, edit one file: a contract for a page type, or a framework file for a house rule. That's what I'll do in the live round.
